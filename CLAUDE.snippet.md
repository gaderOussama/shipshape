# orchestration: Opus orchestrates, Sonnet workers build
On every coding task in every project, work as an orchestrator: plan, split the work, and delegate implementation, research and checks to subagents running on the Sonnet model (Agent tool, `model: "sonnet"`). Opus (the main session) writes the briefs, reviews the workers' diffs and results, and verifies the outcome; it writes or edits code itself only when a worker fails, gets stuck, or produces something wrong that is faster to fix directly. Never give two workers the same files at once. Trivial one-line edits and pure questions can stay in the main session.

# ponytail
- **ponytail** (`~/.claude/skills/ponytail/SKILL.md`) - lazy-senior-dev coding mode, active by default (level: full) on ANY coding task in any project. Read that file and follow its ladder/rules for all code you write, edit, review, or design. Off only if the user says "stop ponytail" / "normal mode". Switch with `/ponytail lite|full|ultra`.

# ship: default dev workflow (on by default)
- **ship** (`~/.claude/skills/ship/SKILL.md`) - the combined best of ponytail, pstack, superpowers and the lifecycle pack (/architect, /test, /check, /audit). On ANY coding task in any project (write, fix, refactor, review code), read that file once per session and follow it without being asked. It picks tier S/M/L by risk itself; `/ship S|M|L` forces a tier, `/ship review` reviews the current diff, `/ship setup` prepares a repo. Off only if the user says "stop ship" / "normal mode".
- ship runs on top of ponytail and the orchestration rule above, not instead of them.
- On coding tasks ship decides which other skills run. superpowers `brainstorming`, `writing-plans`, `executing-plans` and `subagent-driven-development` fire only when the user names them, or for non-code planning, even though their descriptions say "MUST use". ship uses `verification-before-completion`, `receiving-code-review`, `requesting-code-review`'s reviewer template, `dispatching-parallel-agents` and `systematic-debugging`'s technique files directly.

# pstack / poteto-mode (opt-in)
- **poteto-mode** (`~/.claude/skills/poteto-mode/SKILL.md`) - heavy rigor mode. Use only when the user types `/poteto-mode`, or for multi-hour / unattended / multi-PR work that `/ship` routes to it. When active, read that file in full and follow it, opening the `principle-*` and other pstack skills it routes to from `~/.claude/skills/<name>/SKILL.md`.
- Precedence when pstack conflicts with the rules above: (1) subagent model choice follows the orchestration rule (Sonnet workers, Opus reviews), not pstack's model defaults or `/setup-pstack`; multi-model panels (`interrogate`, `arena`, `swarm`) use Claude Code model aliases only (sonnet, opus, fable, haiku; mapping in `~/.claude/rules/pstack-models.md`), never Cursor slugs or Gemini. (2) ponytail and pstack's Laziness Protocol agree; when they pull apart, take the smaller change. (3) poteto-mode's "external actions proceed without asking" does NOT apply: still confirm before sending messages, posting, pushing, deploying or anything outward-facing. (4) Cursor-only steps (bugbot, automations, `cursor-team-kit`, cloud agents) are skipped with a one-line note.
- pstack's own `architect` skill is installed as `pstack-architect` (the lifecycle pack's `/architect` is a different skill). When poteto-mode says "the architect skill", use `pstack-architect`.
- Spawn pstack delegates with `subagent_type: "poteto-agent"` and pass the absolute path above in the prompt.
